# Skyline Cadenza Release Notes (Next Release)

Working draft for the next release. Append entries here as features and fixes land on `main`. At release time this file is renamed to `RELEASE_NOTES_v{version}.md` and `Version` in `src/SkylineCadenza.App/tool-inf/info.properties` is updated to match.

## New Features

- Added a **rank cap** slider ("Rank cap: top N per protein", under Peptide ranking; 0 = no cap, the default). Only the top N precursors of each protein group are eligible for scheduling at all, ranked by whichever peptide-ranking metric is selected - `PrecursorQuantity`, `QValue`, or `PredictedRanking` (Carafe detectability / Bromo score) - applied after the unique-before-razor tier. The cap counts precursors, so a peptide present at two charge states consumes two of the N. In DIA-NN + Carafe backfill mode it is applied per source tier over that tier's own metric, so the confirmed tier keeps its top N by evidence and the predicted tier its top N by predicted score, and neither tier's cap perturbs the other. Distinct from "Maximum peptides per protein", which caps how many of the ELIGIBLE peptides actually get scheduled: the rank cap shrinks the candidate pool (so it also feeds the protein-ordering metrics), while the maximum limits scheduling depth. Guarded by `Scheduler_PeptideRankCap_LimitsGroupToTopRankedByQuantity`, `Scheduler_PeptideRankCap_FollowsQValueRanking`, `Scheduler_PeptideRankCap_FollowsPredictedRanking`, `Scheduler_PeptideRankCap_AppliesPerSourceTier`, and `Scheduler_PeptideRankCapZero_SchedulesEveryEligiblePeptide`.
- Added a **DIA-NN + Carafe backfill** mode (checkbox "Backfill unused schedule time with Carafe predictions", requires both a DIA-NN report and a Carafe library). Confirmed DIA-NN targets are scheduled first (experimental tier); Carafe-predicted targets then fill whatever schedule capacity is left over (predicted tier), deduped against the confirmed targets on peptide + charge. Predictions are scoped to the proteins DIA-NN observed plus any target-protein list, so they add depth to confirmed proteins and cover proteins DIA-NN missed. Backfill breadth-vs-depth follows the selected coverage objective, and predicted peptides respect the same cycle budget and per-protein cap as confirmed ones (a protein already at its Max from experimental peptides gets no predicted ones). The peak-half-width and detectability controls apply to the predicted tier; the status line reports the confirmed + predicted split. Off (default) leaves the previous behavior, where the Carafe library adds no precursors. The experimental tier is now locked: it schedules exactly as it would with no Carafe library loaded (confirmed peptides use their measured DIA-NN fragments, so loading Carafe does not move the empirical schedule), and predicted targets can only add to the leftover cycle budget, never move, drop, or reorder a confirmed target.
- Carafe detectability now also serves as the within-protein **ranking fallback**: when no Bromo ranking file is loaded, peptide priority is driven by Carafe detectability (auto-selecting `PredictedRanking`) instead of the no-signal fragment-intensity stand-in. Bromo, when supplied, still takes precedence for ranking and detectability then only filters.
- The **Bromo peptide ranking** input is now a single-file, Bromo-only selector (Carafe detectability predictions have their own input).
- Added a separate **Carafe detectability predictions** input (multi-file / folder) plus a **detectability cutoff** slider (default 0.5) for the Carafe path. This is independent of the predicted peptide-ranking overlay, so a user can rank with Bromo and filter by Carafe detectability simultaneously. Precursors below the cutoff are dropped before scheduling (peptides with no prediction are kept); the slider rebuilds the candidate pool and reschedules live. Empirical calibration: ~0.5 removes peptides ~90% unlikely to be observed while keeping most real detections.

- Added a configurable **Predicted peak half-width** slider (seconds) for the Carafe path, replacing the hardcoded 0.10 min synthesised peak. Adjusting it rebuilds the Carafe candidate pool and reschedules live; ignored on the DIA-NN / Skyline paths, which use measured peak boundaries.
- Added a predicted peptide-ranking overlay for Carafe-only mode. Supply a Bromo `peptide_rankings.tsv` or Carafe `*_detectability_pred.tsv` (multi-select several shard files, a folder of shards, or one path per line) via the new "Predicted peptide ranking" input. The score is matched onto the Carafe candidate pool by (peptide, charge) and drives a real within-protein peptide priority (`PeptidePriority.PredictedRanking`), which auto-selects when an overlay is loaded. Replaces the no-signal fragment-intensity-sum stand-in documented in `docs/ingest-sources.md`. Within-protein only; it does not affect cross-protein protein ranking.

## Bug Fixes

- **DIA-NN + Carafe backfill no longer re-optimizes the confirmed schedule.** In the combined mode the predicted (Carafe) tier was leaking into the experimental tier through seven shared inputs, so adding backfill changed which confirmed targets were scheduled instead of only adding to the leftover budget. (1) Parsimony was run over the UNION of DIA-NN and Carafe peptides, so the in-silico Carafe peptides re-grouped the confirmed peptides - changing protein-group membership and unique/razor classification, which merged/split groups and pushed confirmed peptides in and out of the per-protein cap. Inside the scheduler: (2) predicted precursors inflated each protein's summed intensity and candidate count, reshuffling the greedy cover order; (3) under Disjoint packing they tightened confirmed slots' growth bounds; (4) shrink-and-place could evict a confirmed target from a slot to seat a prediction; and (5) the RT-bin grid origin was derived from the combined pool. Fixes: parsimony now runs over DIA-NN evidence only and predicted peptides are routed by accession into the confirmed group their protein occupies (`ParsimonyEngine.AssignWithAccessionGroups` + `CandidateBuilder.MapPredictedToExperimentalGroups`); and the scheduler's protein ordering, clash barriers, and grid alignment are computed over confirmed candidates only, with shrink-and-place refusing to evict or re-geometry any slot holding a confirmed member. (6) Enabling backfill auto-switched the peptide-ranking metric to `PredictedRanking` (to rank the predicted tier by detectability / Bromo score), but that metric was applied to BOTH tiers - and confirmed peptides carry no predicted score, so they collapsed to a peptide-ID tie and a different top-N survived the per-protein cap and cycle budget (measured ~32% confirmed-core retention on a real HeLa report). Peptide ranking is now tier-independent: the confirmed tier always ranks by the user's evidence metric (`PrecursorQuantity` / `QValue`) and only the predicted tier ranks by its predicted score, and enabling backfill no longer overwrites the user's ranking choice. (7) Loading a Carafe library replaced the fragment m/z that CONFIRMED peptides use for the MTM interference check (measured DIA-NN Fr.N.Id fragments were overridden by Carafe's PREDICTED fragments), so the empirical schedule shifted merely by loading Carafe - independent of the backfill toggle. Confirmed peptides now schedule on their measured DIA-NN fragments; Carafe's predicted fragments are used only for predicted peptides (and as a fallback for rows with no measured fragments). Fixes: parsimony now runs over DIA-NN evidence only and predicted peptides are routed by accession into the confirmed group their protein occupies (`ParsimonyEngine.AssignWithAccessionGroups` + `CandidateBuilder.MapPredictedToExperimentalGroups`); the scheduler's protein ordering, clash barriers, and grid alignment are computed over confirmed candidates only; shrink-and-place refuses to evict or re-geometry any slot holding a confirmed member; peptide ranking is tier-independent; and confirmed peptides keep their measured fragments. Result: the confirmed schedule is invariant to whether a Carafe library is loaded, and the empirical core is a strict subset of the backfill schedule with predictions only added on top - verified end-to-end on a 32,431-precursor HeLa report + 296,060-precursor Carafe library (100% of the confirmed core retained, plus ~4,400 predicted targets added). Guarded by `Scheduler_ExperimentalCoreUnchangedWhenBackfillReordersProteins`, `Scheduler_ConfirmedTierIgnoresPredictedRankingMetric`, `Scheduler_ConfirmedTierKeepsUserRankingIndependentOfPredictedTier`, `Scheduler_PredictedCannotShrinkOutExperimentalMember`, `Build_PrefersMeasuredDiannFragmentsOverCarafeOverlay`, `AssignWithAccessionGroups_maps_active_collapsed_and_subsumed_proteins_to_their_canon`, and `MapPredictedToExperimentalGroups_routes_by_confirmed_accession_and_parsimonises_the_unseen`.
- **Scheduling is now reproducible across application launches.** The comparator that ranks peptides within a protein was not a total order: peptides tying on the ranking metric (equal `PrecursorQuantity` / q-value / predicted score) kept whatever relative order the unstable sort left them in, which depended on the order the candidate list arrived in. That order was not stable — `CarafeLibraryReader` materialised candidates by enumerating a `Dictionary` keyed on a string-bearing `FragmentKey`, and .NET randomizes string hashing per process. Identical inputs and settings could therefore produce a **different schedule on every app launch** whenever ranking scores tied (measured jaccard 0.58–0.74 between runs on a tied-score pool), so an exported target list and an assay document generated from it could silently disagree — with no indication in either file. The comparator now falls back to `PrecursorId` ordinal order, and `CarafeLibraryReader` returns candidates in a deterministic (modified sequence, charge) order so slot ids and exported row order are stable too. Guarded by `SchedulerDeterminismTests`, which asserts the schedule is unchanged under shuffled candidate order for every coverage objective. Schedules with fully distinct ranking scores were already deterministic and are unaffected.
- Fixed **"No valid precursor m/z column found, line 1"** when pushing an assay whose document contains heavy isotope-labeled standards (e.g. spiked PRTC). Skyline reports a heavy precursor's m/z alongside the bare light sequence, so Cadenza was writing an internally inconsistent transition-list row (light sequence, heavy m/z). Skyline uses an early row to validate the precursor-m/z column, and one such row aborted the entire import with that misleading message. The Skyline-document loader now captures each precursor's `IsotopeLabelType`, the transition-list builder omits heavy-labeled precursors (they can't be applied through Skyline's headless transition-list importer and already reach the assay as heavy via the registered spectral library), and the import now runs with `--ignore-transition-errors` so a single unexpected row can no longer discard the whole scheduled assay. The status line reports how many heavy precursors were omitted.
